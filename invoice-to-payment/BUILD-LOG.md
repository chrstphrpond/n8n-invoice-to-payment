# Build log: CRIT invoicing workflows

What actually came up while building this, in order, and what was done about it. All on 2026-11-15; items 12 to 18 are the fixes after an independent review.

1. **The kit has no factory for three things this set needs.** A Schedule Trigger (its version, 1.4, was read from n8n-mcp `get_node` for n8n 2.42.6), an HTTP Request with a binary body (the PDF upload: `contentType: binaryData`, `inputDataFieldName: data`, schema also from `get_node`), and the Webhook node's `rawBody` option for the HMAC. All three are small helpers in `workflow/flows/common.mjs` built on the kit's factories, so the house rules (retries, `X-Run-Id`, `Idempotency-Key`) still apply. The vendored kit in `_shared/` is unchanged.
2. **The kit's data service has inserts and reads, no update and no sequence.** Invoices change state and need a gap-free number. Rather than edit the kit, `standins/billing-data.mjs` wraps the kit module and adds two routes under the same module name, so they share its tables: a sequence keyed by event id and a compare-and-set update. Their Postgres statements are in SPEC.md.
3. **The kit's Code-node test runner only knows `.first()`.** The reminder and watchdog sweeps handle one item per invoice, so the unit tests use a small runner of their own (`tests/run-code.mjs`) with `.all()`, multi-item input and binary data.
4. **Six node names failed the verb rule.** "Plan", "Spot", "Allocate", "Render", "Void" and "Match" are not in the kit's verb list. The nodes were renamed (Decide invoice plan, Find stuck work, Claim invoice number, Create invoice PDF, Mark invoice void, Decide payment match) instead of widening the list.
5. **Two places returned an array literal starting with a string** (the HTML template's parts, the "body must be an object" error). The kit guide warns that n8n-mcp reads that pattern as a Code node returning bare values; both build the array in a variable first. Validation then passed on the first build: 0 errors in the runtime and strict profiles.
6. **Design change before the first run: no running totals for money.** An invoice row with `paid_minor` updated by each payment would let two payments arriving together both read the old total. Paid and refunded amounts are now always derived from the payment and refund rows; a payment's decision is made against the rows before it and stored on its own row, which a replay reads back.
7. **Design change: a reminder whose run died is reviewed, not resent.** The email API keeps an Idempotency-Key for 24 hours (Resend's documented window), and the next sweep is a day later, so a resend could reach the client twice. A claim taken over from a failed or stuck run now becomes a review item and an alert.
8. **Design change: scheduled runs are off in the tests.** The hourly watchdog could fire in the middle of an end-to-end run and add calls to the exact call lists the tests assert. `INVOICE_SCHEDULES=off` stops the scheduled runs in their first node; the tests start sweeps with signed requests. The two Schedule Triggers themselves are therefore not exercised end to end.
9. **First end-to-end run: 24 of 25.** `invalid_payload` expected a body that is not JSON to reach the workflow and become a dead letter. n8n's webhook parses `application/json` bodies itself and answered 422 ("Failed to parse request body" in the server log) before any node ran. The test now asserts that observed behaviour; the workflow's own path for unparsable bytes is covered by unit tests only.
10. **The e2e lock was held by another run twice.** Both runs waited and went on when it was released, as designed. The receipt scanner's e2e records `lock_released` as "the lock directory is gone", which reads false whenever another run takes the lock straight away; this e2e records whether the lock is still held by its own pid instead.
11. **The first canvas capture was too small to read.** At 2400 x 1500 the portrait-shaped workflows were fitted into a landscape window. Recaptured at 1800 x 2100 with `scripts/capture-canvas.mjs` (throwaway editor in a temporary folder, headless Chrome with a fresh profile, both stopped and the folder deleted afterwards).
12. **Review: two events for one invoice could both decide against the same "before" state.** An independent review found that two `refund.requested` events with different event ids, arriving together, both read an empty refund list and both reached the processor (refunds were unique only by event id), and that two payments arriving together were both recorded `exact` (two receipts, no over-payment review, the second run failing later on the receipt update) or both `partial` (no receipt). Design 6 had removed running totals but not this race. New tests were written first and run against a copy of the previous build: they reproduced each case (two processor refunds; two receipts and a failed run; two `partial` rows; a void invoice with a counted payment and a receipt).
13. **Fix: a money guard on the invoice instead of a lock.** A per-invoice lock would need releasing on every path, and the kit's error workflow only releases ledger claims. Instead every invoice has `money_seq`; a payment row, refund row or void is written only while it still has the value read before deciding, and moves it on in the same step (`standins/billing-data.mjs`: `POST /v1/rows/:table/guarded` and a `guard` on the update; the Postgres statements are in SPEC.md). Two details came up. A lost guard is answered 200 `outcome: conflict`, not 409, because n8n retries any HTTP error 3 times with the same body and key, which would only repeat the stale request. And the guarded write's Idempotency-Key names the counter (`:seq<n>:`), because the stand-in, like Stripe, refuses a reused key with a different body (a unit test that reused one key across two invoices hit that 422). The loser loops back to its first read; `$runIndex` counts the passes and the run stops after 5. The test harness's Code-node runner got `$runIndex`.
14. **A replay no longer writes its payment or refund row again.** With the counter in the key and body, a replay could not resend a byte-identical insert. Replays now go on from the row they find (`replay`, `void_replay`, `refund_resume`, `refund_replay` routes). This also removes a latent failure: once the data service forgot the original Idempotency-Key, the old replay insert would have hit the unique key on `event_id` and failed.
15. **First e2e run of the new scenarios: 6 of 7.** "Check dead letter stored" read `$('Store dead letter').first()`, which is output 0 and empty when the error output fired ("Cannot read properties of undefined"). It now reads its own input: the Respond node passes on whatever Store dead letter gave it.
16. **Late resends.** The previous build disclosed that an invoice or receipt email replayed more than 24 hours after a lost answer would go out twice; the same holds for a refund at the processor. Invoice emails now get an `email_started_at` stamp (service clock, first attempt kept) right before the send; receipts and refunds use their row's `created_at`, which is never later than the send. Within 23 hours the same key is reused; after that the run stops with the ids. The refund replay seen end to end showed n8n answering the sender 500 when the run fails before its answer.
17. **Hygiene.** `.gitignore` uses `*/workflow/exported/` and `*/results/...` patterns (checked with `git check-ignore`). The e2e script writes the per-user temp folder as `<tmp>` in every results file, including the n8n CLI import and publish output the kit harness saves.
18. **Not split.** Moving void and refund into a fourth workflow would need a new endpoint or an Execute Workflow node the kit has no factory for, so "Issue invoices" stays one workflow (65 nodes). Canvas screenshots recaptured with `scripts/capture-canvas.mjs` at 1800 x 2100.
